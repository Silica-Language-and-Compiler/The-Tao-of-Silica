# Interview session — 2026-11-14 (sixth session)

- **Chapter:** 10, Rigor (*Refuse the Almost Right*)
- **Topic:** refusing rather than repairing almost-right code; the gap between
  the published refusal rules and what is built; the compiler generating the
  risky routines; whole-program compilation; the first byte-for-byte
  self-compile; what a refusing compiler opens up
- **Interviewer:** ghostwriter skill
- **Chosen because:** no interview coverage yet, and the 2026-11-14 correction
  (refusal rules are design, not yet built) left an open question about intent.

---

**Q:** The specification's additional rules say values computed and never used,
duplicate work, redundant arithmetic and needless repetition should all stop the
build, as errors with no switch to turn them off. The implementation-status
table shows only the first is built. Is publishing the full set before building
it a deliberate choice, a statement of intent the language holds itself to, or
is it simply that the compiler hasn't caught up yet?

**A:** The compiler hasn't caught up yet.

**Q:** In the Chapter 3 session you said the first dishonesty you noticed was the
optimizer. That explains distrusting optimizers. But refusing goes further: a
compiler could just leave almost-right code alone, neither repairing nor
refusing it. Why wasn't leaving it alone enough? When did you decide that
almost-right code should actually stop the build?

**A:** unused code makes the code more complex and offers yet another attack surface for bad actors. We should clean up after yourself at work, home, and when visiting, we should clean up after ourselves when code changes are made.

**Q:** Unused code as complexity and as attack surface. Most programmers treat
dead code as clutter, not danger. Have you seen a case — industry, the 2024
security research, SEMP — where code nobody was using turned out to be the way
in? What first showed you leftovers are a security problem, not just untidiness?

**A:** I have no example. Just thinking and extrapolation. Every line of code written is a line of code that could have a bug in it. get rid of what is not needed.

**Q:** "Every line is a possible bug" weighs more now that an army of LLM
developers can produce a great deal of code fast, and models are known for
leaving things behind: helpers nobody calls, values computed and dropped, work
done twice. Has the strict compiler changed how you work with the models? Do the
refusals act as a check on what they produce, the way effect errors tell them
exactly where the fix goes?

**A:** It acts as a check and verification of what they have done. The errors tell you exactly what to remove so an LLM can readily remove them.

**Q:** On 12 September 2026 Silica's compiler, written in Silica, first compiled
itself and produced exactly the same result, byte for byte. Take me to that day.
What were you doing when the match came through, and what did it mean to you?
A milestone you'd been chasing, or did it arrive quietly?

**A:** I was watching the compile. It took a few attempts to get all the runtime leftovers from the Rust build removed. It took a few days.

**Q:** The last obstacle was leftovers from the Rust bootstrap that had to be
cleared out. Once they were gone and the bytes matched, did Silica stand fully on
its own, with Rust no longer needed to build it? And what did you feel watching
that final compile come out identical?

**A:** after this, I could remove all Rust dependencies. Clang became the linker and assembler of choice. I did this because unused tools should be removed from devices as well. For the same reasons that unused code should be removed.

**Q:** For a team, or a class of students, working every day with a compiler that
won't accept almost-right code and points to exactly what to remove, what
becomes possible that a generous compiler, one that warns and moves on, doesn't
allow?

**A:** The LLM generated code is more succinct, more likely to be correct, and more likely to safer. all this at scale.

**Q:** Silica compiles an application as one program, seen whole, with libraries
as source. Erlang is famous for updating a running system in place without
stopping it. Does seeing the program whole rule that out for Silica, or is there
a way to replace a running piece and still keep the guarantees that come from
seeing everything at once?

**A:** This is something that I'm actively thinking about and haven't settled on a solution yet. Is there one? Yes. I'm just not ready to talk about it at this point.
